# Fork changes

This fork (`AlexFrontegg/paperclip`, deploy branch `deploy`) adds the features below on top of `paperclipai/paperclip`. Use this list when merging an upstream release: every hook point must still exist after the merge, and every proving test must pass.

## Usage-limit fallback

When an agent's primary AI hits its usage limit, stops responding twice in a row, or its account is signed out, the agent runs on a second adapter and AI connection until the primary is back. Design: [plans/2026-10-06-usage-limit-fallback.md](plans/2026-10-06-usage-limit-fallback.md).

Core:
- `packages/shared/src/usage-limit-fallback.ts`: config, state and helpers. `validators/agent.ts` accepts `runtimeConfig.usageLimitFallback`.
- `server/src/services/usage-limit-fallback.ts`: activation, suspension, the effective agent for a run, and the adapter chosen at claim.

Hook points:
- `heartbeat.ts` `executeRun`: the run executes `effectiveAgentForRun(storedAgent, run)`; fallback runs drop the issue's engine overrides; a resume from a run on another adapter starts fresh; a deferred fallback retry is scheduled after cleanup.
- `heartbeat/retries.ts`: `scheduleBoundedRetryForRun` switches to the fallback on a quota or repeated outage failure, and picks Codex's transient retry mode from the failed run's claimed adapter; `handleUsageLimitFallbackAccountFailure`; `deferredUsageLimitFallbackRetries`.
- `heartbeat/queue.ts`: the claim stores `adapterDispatch` from `resolveAdapterDispatchForClaim`.
- `heartbeat/scheduling.ts`: a quota recovery monitor lets the other lane take the attempt.
- `heartbeat/run-completion.ts`: account failures go to the fallback handler; a turn on either lane clears the other lane's task session (inside upstream's `persistSessionState`, so it also covers the case-handoff path).
- `heartbeat/run-control.ts`: release waits for a deferred fallback retry; Stop sends SIGINT by the claimed adapter.
- `heartbeat/run-state.ts`: `dispatchedAdapterType` in run lists; a session reset clears the fallback's sessions and keeps the fallback state.
- `heartbeat/session-preparation.ts`, `heartbeat/execution-configuration.ts`, `execution-workspace-policy.ts` (`withoutFallbackEngineOverrides`).

Callers: the retry gate and queued-run check in `connectionContinuationPendingResponse` and `modules/run-dispatch/adapters/postgres.ts`; the legacy follow-up in `recovery/disposition-repair.ts` (`collectDispositionRepairSourceState` and `readDispositionRepairDurableWaitingState`); the native follow-up in `heartbeat/run-lifecycle.ts` (`handleSuccessfulRunHandoff`).
- `lib/agent-records.ts` and `services/agent-hiring.ts`: a hire installs the fallback AI connection.

**Codex out of credits:** a Codex workspace that is out of credits counts as a provider quota failure, so the fallback takes over. Only Codex's own error reports count (`error` and `turn.failed` events, plain CLI lines), never tool output or agent text in item events, so a crash on a repo that mentions "usage limit" does not start the fallback (`codexErrorReportLines`). Hook points: the quota patterns and `isCodexProviderQuotaError` in `packages/adapters/codex-local/src/server/parse.ts`, and `acp.ts`. Proving tests: `packages/adapters/codex-local/src/server/parse.test.ts`, `acp.quota.test.ts`.

**Paperclip Runner agents:** a Runner agent that runs Claude Code or Codex can have a fallback, which runs on the Claude Code or Codex adapter directly. Detection is upstream's (`e37ab23dbc`, below): the Runner ends a turn on the account's limit with `native_provider_usage_limit`, for Codex's `usageLimitExceeded` and for a Claude limit whose title the Runner types as `quota_exhausted` or `rate_limit`. Turn, budget and context limits stay `native_provider_terminal_failed`.
- The executor hands a `native_provider_usage_limit` turn to the fallback unless its `providerFailure` is a `rate_limit`, which clears within minutes. Before it fails the run, it turns the fallback on in a transaction of its own (`handRunnerTurnToUsageLimitFallback`), so the agent's other work, claimed once the run frees its slot, already takes the fallback lane instead of waiting in upstream's hold. That activation is the hand-off decision: if it fails, the task is blocked as upstream does. The window comes from the handed-off failure, read at its own time, and from the agent's other recent limits (`agentProviderLimitCooldown`, at most 24 hours, so a weekly limit tries the primary once a day).
- The real Runner checkpoints its failed terminal before it raises the typed failure, and upstream reads that checkpoint as ambiguous provider state. That ambiguity, and only that one, is accepted: the executor hands off when the error is the Runner's own `NativeProviderTerminalFailure`. Another error after the usage-limit turn, a remote Runner target, unverified runner ownership, rate, turn and budget limits, and agents without a usable fallback still block the task as upstream does.
- When the run still owns its task, the executor neither blocks the task nor opens its board card. It marks the failed run `resultJson.usageLimitFallbackHandoff` and stores the handed-off failure as the run's `providerFailure` (otherwise the run keeps its first attempt's), so upstream's hold reads the same reset. It marks the native coordinator's `failureDetail` too, and `projectExecution` shows such a run without a card as "Continued on usage-limit fallback", not "Recovery needed". A task that moved away from the run (closed, blocked or reassigned) gets no mark and no retry; the fallback still takes the agent's other work.
- The failure handler (`handleUsageLimitFallbackAccountFailure`) only schedules the fallback's turn for a marked run: right away, or at the window's end if the fallback was suspended meanwhile. The turn has a retry attempt of its own. A native run's retry is never deferred until after cleanup, because a user's continuation admits only a legacy retry. So when no retry can be scheduled, for example for a user's explicit continuation, the release finds no successor and upstream's release blocks the task with a board card (`recordNativeTerminalRecoveryIfNeeded`); the user's next retry runs on the fallback. Remaining gap: a server crash between the executor's commit and the failure handler leaves the task in progress with no run, because upstream's stranded-task sweep skips native runs.
- The safe-replacement sweeper never selects these runs (`nativeReplacementPending` leaves out `native_provider_usage_limit`), so no replacement marker is needed.
- Upstream's provider-limit hold (`heartbeat/provider-limit-wait.ts`) never holds a run that executes on the fallback. Its evidence leaves out fallback-lane runs, so the fallback account's limit does not hold the primary, and a fallback success does not end the primary's limit. Primary-lane runs keep upstream's hold, for example while the fallback is suspended. The fallback account's own limit holds neither lane on purpose: the run that hit it waits for the earlier of that reset and the primary's return, and each new wake starts once and fails fast. Holding the fallback lane on its own evidence would need a cap at the window and per-user evidence for personal fallback accounts inside upstream's `provider-limit-wait.ts`.
- "Return to primary" ends the hold for limit evidence from before it: `agentProviderLimitCooldown` ignores runs that finished before `usageLimitFallbackReturnedAt`, for every adapter, so the next wake runs on the primary. A limit the primary reports afterwards holds again.
- The fork also reads a reset on a named day (`parseProviderQuotaClockReset`): Claude's weekly and two-day titles, "resets Nov 12 at 6:49am (UTC)", and Codex's "try again at Nov 9th, 2026 4:30 PM". Upstream reads only a clock and waits one hour without it. A named day is its nearest occurrence, so a late read gives a past reset, not next year's; a date without a clock time is not read. Upstream's quota recovery for direct adapters (`classifyAdapterFailureForRecovery` in `recovery/service.ts`) reads named days too, and uses a parsed reset only while it is in the future.
- Hook points: the failure handler in `native-runtime/native-session-executor.ts` (`usageLimitFallbackActivated` before the failure transaction; inside it, `stillOwnsTask` moved up and `handedToUsageLimitFallback`, which skips the block and the card and writes the marks, the handed-off `providerFailure` and the coordinator's `nextAction`); `execution-projection.ts` (the "Continued on usage-limit fallback" branch); `usage-limit-fallback.ts` (`handRunnerTurnToUsageLimitFallback`, `runnerTurnHandedToFallback`); `packages/shared/src/usage-limit-fallback.ts` (`RUNNER_USAGE_LIMIT_HANDOFF_KEY`, `USAGE_LIMIT_FALLBACK_RETURNED_AT_KEY`, and `usageLimitFallbackConfigProblem`, which reads the Runner's agent with `agentHarnessType`); `heartbeat/retries.ts` (`scheduleRunnerUsageLimitFallbackTurn`, called from `handleUsageLimitFallbackAccountFailure`; `oneMoreRetryAttempt`; `scheduleUsageLimitFallbackRetry` defers only legacy runs); `heartbeat.ts` (the exemption at the `deferRunForProviderLimit` call, `agent === storedAgent`); `agentProviderLimitCooldown` in `native-runtime/native-startup-retry.ts` (the fallback-lane and Return-to-primary filters); `provider-quota-reset.ts` (named days); `recovery/service.ts` (`classifyAdapterFailureForRecovery` uses only a future parsed reset); `ai-health.ts` (selects `provider` and `acpxAgent`); UI `UsageLimitFallbackField.tsx`.
- Proving tests: `server/src/services/native-runtime/native-usage-limit-fallback.integration.test.ts` (the Runner's checkpointed failed terminal with Codex's limit and Claude Code 2.1.286's titles: the hand-off, activation before the run fails, the window from the handed-off failure, the fallback's turn through the failure handler and the release, the projection, the exclusions, a task that moved away, the release without a retry, and a user's explicit continuation); `packages/paperclip-runner/src/drivers/usage-limit-titles.test.ts` (the Runner types the real titles as those tests replay them); the "a Paperclip Runner turn the executor left to the usage-limit fallback" tests in `server/src/services/heartbeat/retries.test.ts`; in `server/src/__tests__/heartbeat-usage-limit-fallback.test.ts`, "runs the fallback while the primary's provider limit holds only the primary's work", "lets fallback-lane work start despite the fallback account's own limit; only the failed run's retry waits", "does not hold the primary for the fallback account's own limit", "runs the primary again after Return to primary, despite its earlier limit" and "still holds the primary for a limit it reports after Return to primary"; `server/src/services/provider-quota-reset.test.ts`; the late dated reset case in `server/src/services/recovery/provider-failure-classification.test.ts`; upstream's `server/src/__tests__/heartbeat-provider-limit-wait.test.ts`; the Runner cases in `packages/shared/src/usage-limit-fallback.test.ts` and `ui/src/components/UsageLimitFallbackField.test.tsx`.

## Chat messages wake blocked tasks

A message in a connected chat conversation (Slack and the other chat providers) wakes a task that is blocked or paused, as a comment does. Upstream issues #15040 and #15974. A paused tree admits only a message that a linked person wrote; a guest's message, a bot's message and an automatic GitHub event stay held (`isPersonChatMessage`).
- Hook points: `EXTERNAL_CHAT_MESSAGE_WAKE_REASON` in `packages/shared/src/types/chat-channels.ts`, used by `server/src/services/chat-channels/inbound/wakeups.ts` and listed in the interaction wake reasons of `server/src/services/issue-tree-control.ts`, which also matches the chat wake's `wakeCommentId`.
- Proving test: `server/src/__tests__/heartbeat-dependency-scheduling.test.ts`.

## Linear-time scan of long base64 blobs

Long base64 blobs in run logs no longer make the secret patterns scan in quadratic time and freeze the server: the name patterns start with a lookbehind instead of `\b`. Only that case is fixed: redacting many quoted `authorization:` values is still quadratic in upstream's code (64 KB takes about 1 s).
- Hook points: `packages/adapter-utils/src/command-redaction.ts`, `server/src/redaction.ts`.
- Proving tests: `packages/adapter-utils/src/command-redaction.test.ts`, `server/src/__tests__/redaction.test.ts`, `server/src/__tests__/heartbeat-run-log.test.ts`.

## Merging an upstream release

1. Branch from `deploy` and merge the upstream tag.
2. For the GitHub bot files, combine upstream's changes with `deploy`'s fork versions (`ports/github-bot` is only a reference).
3. For the fallback, keep upstream's code and re-apply the hook points above.
4. Type-check `server` and `ui`, and compare with upstream's own errors at the tag. The server type check skips `src/__tests__`, so a broken test merge shows up only when the test runs.
5. Run every proving test file above in full, not filtered by test name.
6. Right after the deploy, turn on **Settings → Experimental → GitHub review bots** (`enableGitHubReviewBots`, off by default since v2026.1023.0). Until then the bot keeps reviewing, but its settings page redirects away and GitHub identity linking returns 403, so new members' pull requests are not reviewed.
